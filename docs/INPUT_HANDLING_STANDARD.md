# INPUT_HANDLING_STANDARD

Стандарт приёма пользовательского ввода для подключаемого модуля списка.

**rev 3.1 — 2026-07-23.** Заменяет rev 2 целиком. Отличия от rev 3 — §0.

---

## 0. Статус документа

Это стандарт, а не описание конкретной кодовой базы. Он не привязан к
репозиторию, фреймворку и бэкенду: любое приложение, встраивающее модуль
списка, обязано соблюдать §2–§7, и любая реализация, соблюдающая их,
считается совместимой.

**Что отменено относительно rev 2.** В rev 2 модуль ввода различал два
жеста (тап и удержание), свайп игнорировался, а сдвиг пальца более ~12 px
отменял начатую запись и закрывал оверлей. Это отменено. В rev 3 сдвиг
пальца — основной механизм выбора, а свайп влево — способ прицепить
контекст. Реализации rev 2 несовместимы с этим документом.

**Что изменено в rev 3.1** — устранение неоднозначностей, найденных при
сверке с кодом:

- Функция распознавателя переименована в `resolveCommands`: имя `resolve`
  уже занято резолвером цели (§8.3), и совпадение имён у двух разных
  контрактов путало.
- Задана формула выбора строки по смещению пальца (§5).
- Определено поведение при свайпе после взвода, при повторном касании и
  момент старта записи (§4).
- Команда поиска названа `showSearch` — по правилу журналирования (§7)
  видовые команды опознаются по префиксу `show`.
- Открытые вопросы rev 3 закрыты решениями (§13).

**Смежные документы.**

| Документ | Что определяет |
|---|---|
| `TASK_RESOLVER.md` | Алгоритм сопоставления цели по нечёткому вводу, параметры Θ. Реализация — `resolver.js`. Зафиксирован как решение |
| `PROPOSAL_voice-input.md` | Привязка этого стандарта к конкретному репозиторию: адаптеры, имена полей, этапы |

## 1. Концепция

Модуль списка — самодостаточный компонент, который PWA-приложение
подключает к себе, чтобы получить иерархический список и голосовое
управление им. Приложение отвечает за данные и за домен; модуль отвечает
за то, как пользователь выражает намерение и как это намерение
превращается в команду.

Поток однонаправленный, три слоя:

```
жест + речь  →  ПРИЁМ ВВОДА  →  РАСПОЗНАВАТЕЛЬ  →  ИСПОЛНИТЕЛЬ  →  патч
                  (§3–§5)         (§6)              (§7)
```

Приём ввода не знает бизнес-логики. Распознаватель не изменяет состояние.
Исполнитель не разбирает текст. Слои не перепрыгиваются.

**Три сущности с похожими именами — не путать:**

| Имя | Что это | Где определён |
|---|---|---|
| `resolveCommands(text, context, snapshot)` | Распознаватель: текст → кандидаты-команды | §6 |
| `resolver.resolve(text, rows)` | Резолвер цели: текст → `One \| Vector \| Empty` | `TASK_RESOLVER.md`, `resolver.js` |
| `execute(state, command)` | Исполнитель: команда → патч | §7 |

Распознаватель **вызывает** резолвер цели для команд с целью (§8.3).
Обратной зависимости нет.

### Принципы

1. **Один жест — носитель всего голосового управления.** Не существует
   отдельных кнопок записи, режимов и модальностей помимо описанных в §4.
2. **Подтверждение до исполнения, а не отмена после.** Пользователь видит
   команду, которая будет выполнена, прежде чем отпустить палец.
   Единственное исключение — фолбэк на модель (§9).
3. **Речь и текст неразличимы ниже слоя приёма.** Транскрипт и строка,
   введённая с клавиатуры, проходят одну грамматику и один путь.
4. **Всё, что доступно пользователю, доступно тестирующему агенту** через
   тот же контракт, без отдельной ветки логики (§11).
5. **Модуль не владеет данными.** Он получает снимок и отдаёт патч.

## 2. Границы с приложением-хостом

### Что предоставляет модуль

- Разметку и монтирование интерактивных элементов списка (§3).
- Обработку жестов и полноэкранный оверлей (§4–§5).
- Распознаватель и базовый словарь команд (§6, §8).
- Формат записи журнала действий (§10).
- Тестовый хук (§11).

### Что обязан предоставить хост

| Ресурс | Требование |
|---|---|
| Снимок списка | Плоский массив элементов, каждый с полями по таблице ниже |
| Адаптер снимка | Приведение полей хоста к именам, которые ждёт резолвер цели: `{id, title, status}` со `status ∈ {open, closed}`. Резолвер `resolver.js` не переписывается под хост — адаптируется вход |
| Исполнитель | Реализация контракта §7, покрывающая обязательный минимум команд |
| ASR-адаптер | Источник промежуточного и финального транскрипта |
| Фолбэк-канал | Точка, принимающая сырой транскрипт и возвращающая команду (§9) |
| Персистентность | Куда уходит патч после исполнения — дело хоста; модуль этого не видит |

Обязательные поля элемента снимка:

| Смысл | Обязательность |
|---|---|
| Идентификатор | Обязательно, уникален |
| Родитель | Обязательно, `null` для корня |
| Порядок среди соседей | Обязательно |
| Статус | Обязательно |
| Отображаемый текст | Обязательно — по нему работает резолвер цели |

Имена этих полей задаёт хост и объявляет в адаптере снимка. Модуль не
предполагает конкретных имён.

### Чего модуль не делает никогда

- Не решает, где хранятся данные, и не обращается к хранилищу напрямую.
- Не выполняет сетевых запросов иначе как через фолбэк-канал хоста.
- Не рендерит доменные экраны приложения (карточки, настройки, отчёты) —
  он только сообщает хосту, что их следует открыть, через `effect` (§7).
- Не хранит состояние между жестами, кроме параметров конфигурации.
- Не разрешает расхождения снимка с источником данных (§13.3).

### Точки расширения

Хост может: добавить свои команды в словарь распознавателя; переопределить
действие тапа для конкретного `agent-action-id`; переопределить любую
константу §4. Всё остальное менять нельзя, иначе теряется совместимость.

Переопределения тапа задаются **единой таблицей** `elementId → действие` в
одном месте. Разбрасывать их по коду рендера запрещено (§12).

## 3. Маркировка элементов

Каждый интерактивный элемент обязан нести атрибут `agent-action-id` с
уникальным в пределах страницы значением: идентификатор элемента списка,
идентификатор строки журнала или фиксированное имя кнопки.

Элементы без `agent-action-id` не интерактивны и модулем не
обрабатываются. Элемент, доступный пользователю, но не помеченный, —
нарушение стандарта, а не «неинтерактивный элемент».

## 4. Жесты

Распознаются три жеста. Все остальные (мультитач, свайп вправо, удержание
вне списка без речи) игнорируются молча.

| Жест | Условие | Результат |
|---|---|---|
| **Тап** | Касание короче `LONGPRESS_MS`, смещение меньше `ARM_SLOP_PX` | Действие элемента по таблице переопределений; по умолчанию — открыть поле ввода с кнопкой «Отправить» |
| **Удержание** | Касание в любой точке экрана дольше `LONGPRESS_MS` при смещении меньше `ARM_SLOP_PX` | Взводится оверлей **без контекста** |
| **Свайп влево по элементу** | Начато на элементе списка; горизонтальное смещение достигло `CONTEXT_DX_PX` при `|dx| > CONTEXT_RATIO · |dy|` в пределах `CONTEXT_WINDOW_MS` от начала касания | Взводится оверлей **с контекстом**; контекст — элемент, на котором палец находился в момент свайпа |

### Приоритет прокрутки

До взвода оверлея прокрутка выигрывает всегда. Вертикальное смещение
больше `ARM_SLOP_PX` до истечения `LONGPRESS_MS` отменяет жест целиком и
отдаёт движение скроллу. Слушатели регистрируются как `passive` вплоть до
момента взвода.

После взвода прокрутка блокируется, и всё движение пальца
интерпретируется как выбор в оверлее.

Свайп влево — исключение: он взводит оверлей немедленно, не дожидаясь
таймера. Проверка соотношения `|dx| > CONTEXT_RATIO · |dy|` отсекает
диагональное движение, поэтому обычная прокрутка его не запускает.

### Краевые случаи (заданы явно, не на усмотрение реализации)

1. **Свайп после взвода.** Горизонтальное движение после того, как
   оверлей взведён, игнорируется. Контекст фиксируется один раз, в момент
   взвода, и в течение жеста не меняется.
2. **Взвод без контекста поверх элемента.** Удержание на элементе списка
   даёт оверлей **без** контекста. Контекст даёт только свайп влево.
3. **Начало записи.** Микрофон включается в момент взвода оверлея, не
   раньше. Речь до взвода не захватывается.
4. **Второе касание во время жеста.** Игнорируется целиком; жест
   продолжает вести первый палец.
5. **Прерывание системой** (звонок, сворачивание, потеря фокуса) —
   равносильно отмене: оверлей закрывается, команда не исполняется,
   в журнал пишется событие отмены.
6. **Пустой транскрипт при отпускании вне зоны отмены** — равносильно
   отмене.

### Константы

| Константа | Значение | Смысл |
|---|---|---|
| `LONGPRESS_MS` | 400 | Удержание до взвода оверлея |
| `ARM_SLOP_PX` | 10 | Допуск на дрожание пальца до взвода |
| `CONTEXT_DX_PX` | −40 | Порог горизонтального сдвига для контекстного режима |
| `CONTEXT_RATIO` | 2 | Отношение горизонтали к вертикали для отсечки прокрутки |
| `CONTEXT_WINDOW_MS` | 250 | Окно от начала касания, в котором свайп засчитывается |
| `DEADZONE_PX` | 16 | Мёртвая зона вокруг точки пальца |
| `ROW_H_PX` | 48 | Высота строки кандидата |
| `CANCEL_ZONE_PX` | 56 | Отступ вниз до зоны отмены |
| `FREEZE_DY_PX` | 24 | Сдвиг вверх, после которого порядок кандидатов замораживается |
| `MIN_HOLD_MS` | 150 | Отпускание раньше при пустом транскрипте — отмена |

## 5. Оверлей

Оверлей занимает весь экран. Вне его интерактивных элементов нет.

### Зоны, сверху вниз

1. **Транскрипция** — у верхней границы, обновляется в реальном времени.
2. **Чип контекста** — под транскрипцией, только в контекстном режиме;
   показывает элемент, к которому будет применена команда. Пользователь
   обязан видеть его до отпускания.
3. **Стек кандидатов** — вверх от пальца, ближайший к пальцу наиболее
   вероятен, дальше по убыванию. Высота строки `ROW_H_PX`, длина стека не
   больше `CAND_LIMIT` из `resolver.js`.
4. **Точка пальца** — «как есть»: отпускание без смещения отправляет сырой
   транскрипт (§9). Мёртвая зона `DEADZONE_PX`.
5. **Зона отмены** — ниже точки пальца дальше `CANCEL_ZONE_PX`. Отпускание
   здесь не делает ничего, кроме записи в журнал.

### Выбор строки по смещению

`dy` — смещение пальца вверх от точки взвода в пикселях (вверх
положительно):

| Условие | Что выбрано |
|---|---|
| `dy ≤ −CANCEL_ZONE_PX` | Отмена |
| `−CANCEL_ZONE_PX < dy < DEADZONE_PX` | «Как есть» (сырой транскрипт) |
| `dy ≥ DEADZONE_PX` | Кандидат с индексом `min(⌊(dy − DEADZONE_PX) / ROW_H_PX⌋, N−1)`, где `N` — длина стека |

Если стек пуст, зона кандидатов не существует: любое `dy ≥ DEADZONE_PX`
равносильно «как есть».

Если места вверх не хватает, стек прижимается к нижней границе зоны
транскрипции и прокручивается; зоны 4 и 5 не смещаются, формула выбора
применяется к прокрученному стеку.

### Правила поведения

- **Живой пересчёт.** Кандидаты пересчитываются по промежуточному
  транскрипту.
- **Заморозка.** Как только палец сместился вверх на `FREEZE_DY_PX`,
  порядок кандидатов фиксируется. Пересчёт продолжается, но строка под
  пальцем не может подмениться. Без этого пользователь выберет не то, что
  видел.
- **Коммит по финальному транскрипту.** Отпускание не исполняет команду на
  промежуточном результате: модуль дожидается финала, удерживая выбранную
  позицию. На время ожидания оверлей остаётся на экране с индикатором.
- **Стабильность идентификаторов.** Кандидат сохраняет идентификатор между
  пересчётами, иначе заморозка неосуществима.

### Специализация стека по типу намерения

| Намерение | Точка пальца | Стек вверх |
|---|---|---|
| Поиск | Показать найденное | Уточняющие кандидаты запроса |
| Добавление | Добавить с распознанным текстом | Найденные дубли; выбор дубля отменяет добавление и открывает существующий элемент |
| Команда с целью | Наиболее вероятная цель | Остальные кандидаты цели |

Единое правило: **вверх идут кандидаты разрешения цели**, а не смесь
команд и сущностей. Глагол определяется речью и отображается заголовком
стека.

## 6. Контракт распознавателя

Распознаватель — чистая функция от текста, контекста и снимка списка.
Состояние он не меняет и в сеть не ходит.

```
resolveCommands(text, context, snapshot) → Candidate[]
```

- `text` — текущий транскрипт (промежуточный или финальный) либо строка из
  поля ввода.
- `context` — идентификатор элемента или `null`.
- `snapshot` — актуальный снимок списка от хоста.

Кандидат несёт всё необходимое и для отрисовки, и для исполнения:

| Поле | Назначение |
|---|---|
| `id` | Стабилен между пересчётами |
| `kind` | `command` или `entity` |
| `label` | Что видит пользователь |
| `hint` | Вторая строка: путь, статус, родитель |
| `score` | Ранг, определяет порядок в стеке |
| `command` | Готовая к исполнению команда по §7, либо `null`, если слот не заполнен |

Кандидат с `command = null` отображается, но не исполняется: отпускание на
нём равносильно отмене (§8.3).

### Три исхода отпускания

| Где отпущен палец | Что происходит |
|---|---|
| В мёртвой зоне | Сырой транскрипт уходит в фолбэк (§9) |
| На кандидате | `candidate.command` уходит исполнителю |
| В зоне отмены | Только запись в журнал |

## 7. Контракт исполнителя

```
execute(state, command) → { patch, actionLogEntry, viewMode?, effect? }
```

Команда — объект `{ command, actId, payload }`, где `actId` — цель
команды: идентификатор элемента, к которому она применяется, или
`null`/`'list'` для команд над списком целиком.

Команды делятся на два класса, и разделение обязательно:

- **Мутирующие** — возвращают патч и запись журнала.
- **Видовые** — меняют то, что показано, возвращают `viewMode` или
  `effect`, патч пустой, **запись журнала не создаётся**.

**Правило опознания класса:** имя видовой команды начинается с `show`
либо равно `viewItem`. Это машинная проверка в исполнителе, а не
соглашение — поэтому команда поиска называется `showSearch`, а не
`search`.

### Обязательный минимум

| Команда | Класс | Смысл |
|---|---|---|
| `addItem` | мутирующая | Новый элемент в корень |
| `addChild` | мутирующая | Новый ребёнок элемента `actId` |
| `editItem` | мутирующая | Правка текста |
| `setParent` | мутирующая | **Новая.** Смена родителя элемента `actId` |
| `setStatus` | мутирующая | Смена статуса |
| `setTags` | мутирующая | Переключение тега |
| `toggleCollapse` | мутирующая | Сворачивание поддерева |
| `deleteItem` | мутирующая | Удаление вместе с поддеревом |
| `reorderItems` | мутирующая | Изменение порядка |
| `undo` | мутирующая | Откат по снимку из `payload` |
| `showSearch` | видовая | **Новая.** Показать выборку по запросу |
| `showList`, `showFrontier`, `showActionLog` | видовые | Переключение вида |
| `viewItem`, `show*Modal` | видовые | Открытие доменного экрана хоста через `effect` |

`setParent` и `showSearch` в существующих реализациях отсутствуют и
требуются новым словарём (§8).

**Ограничение `setParent`:** перенос элемента в самого себя или в любого
своего потомка запрещён — исполнитель обязан отвергнуть такую команду без
патча и без записи журнала. Распознаватель обязан не показывать такие
цели в стеке кандидатов.

## 8. Команды

### 8.1 Без контекста

| Формы | Действие |
|---|---|
| «найди …», «покажи …» | `showSearch` |
| «добавь …», «нужно …», «мне нужно …», «нужно сделать …», «новая …» | `addItem` |

Куда попадает новый элемент без контекста — определяет хост. Если у хоста
нет выделенного inbox, элемент создаётся в корне.

### 8.2 С контекстом

| Формы | Действие |
|---|---|
| «добавь подзадачу …», «подзадача …», «тут сначала нужно …», «добавь блокер …», «сначала сделать …» | `addChild` с `actId` = контекст |
| «перенеси в …», «сделай подзадачей в …» | `setParent`: `actId` = контекст, новый родитель — цель из стека |

Один и тот же глагол «добавь» означает разное в зависимости от наличия
контекста. Поэтому чип контекста (§5) обязателен: без него пользователь не
может отличить два исхода до отпускания.

### 8.3 Команды с целью

Команда с целью — та, где часть речи должна быть сопоставлена с конкретным
элементом списка: цель поиска, кандидат-дубль при добавлении, новый
родитель при переносе.

Сопоставление выполняется **алгоритмом из `TASK_RESOLVER.md`**, вызов —
`resolver.resolve(text, rows)`. Там же формальное описание параметров Θ,
ярусы совпадения токенов, правила выбора и реализация `resolver.js`.
Стандарт фиксирует только границу и отображение результата на интерфейс:

```
resolver.resolve(text, rows) → One(id) | Vector([...]) | Empty
```

| Исход | Что показывает оверлей |
|---|---|
| `One` | Единственный кандидат у пальца, стек пуст |
| `Vector` | Кандидаты в стеке в порядке убывания ранга |
| `Empty` | Стек пуст, точка пальца — «не найдено», исполнение невозможно |

Охват поиска и параметры Θ определяются `TASK_RESOLVER.md`; дублировать их
здесь запрещено. Приведение снимка хоста к форме `rows` — задача адаптера
снимка (§2).

**Два слота.** «Перенеси в …» требует и контекст, и цель. Контекст даёт
свайп, цель даёт стек. Если цель не выбрана — отпускание равносильно
отмене. Команда с незаполненным слотом никогда не исполняется частично.

## 9. Фолбэк на модель

Отпускание в мёртвой зоне отправляет сырой транскрипт через фолбэк-канал
хоста. Сервер возвращает готовую команду, которая исполняется тем же
исполнителем (§7), что и локально распознанные.

- Путь не требует синхронизации с бэкендом данных: команда возвращается на
  фронт и применяется к локальному состоянию.
- **Оптимистичного применения нет.** Модуль не знает, какую команду вернёт
  модель, поэтому применить её заранее невозможно. Оверлей закрывается
  сразу, на месте будущего изменения показывается индикатор ожидания,
  список меняется только по ответу.
- Когда модель определила команду, показывается тост.
- Результат попадает в журнал действий и отменяется оттуда наравне с
  остальными (§10). Это единственное место, где отмена происходит **после**
  исполнения, а не до.
- **Канал недоступен** (нет сети, ошибка, таймаут): сырой транскрипт
  создаётся как новый элемент через `addItem`, запись журнала помечается
  как нераспознанная, показывается тост. Речь пользователя не теряется,
  действие отменяется одним `undo`. Ждать сети и копить очередь — нельзя.

## 10. Журнал и отмена

Каждая мутирующая команда создаёт запись журнала: идентификатор, время,
исходная команда, патч, человекочитаемая подпись, статус синхронизации.
Видовые команды записей не создают.

Показ оверлея и отмена фиксируются как события журнала без патча — это
делает разбор промахов распознавания возможным постфактум.

Отмена из журнала выполняется командой `undo`: в `payload` кладётся
снимок, сохранённый до применения отменяемой записи. Хранение снимков —
обязанность журнала.

## 11. Тестируемость

**Поле ввода.** Дефолтное действие тапа — открыть поле ввода с кнопкой
«Отправить». Отправка вызывает распознаватель с тем же `elementId` и тем
же текстом, что дала бы речь. Это основная поверхность автотестов: агент
проходит полный путь пользователя без синтеза речи.

**Прямой хук.** Дополнительно открывается точка вызова в обход касаний,
задокументированная комментарием рядом с кодом. Хук обязан повторять
контракт §6 ровно, без собственной валидации и без отдельных веток.

**Воспроизводимость.** Действующие значения констант §4 и параметров Θ
пишутся в журнал при каждом показе оверлея. Любая запись журнала должна
быть воспроизводима без знания того, какая конфигурация стояла в тот день.

## 12. Что запрещено

- Создавать слушатели событий на элементах вне единого модуля приёма.
- Ветвить интерпретацию ввода по типу элемента внутри слоя приёма.
- Переопределять действие тапа где-либо, кроме единой таблицы (§2).
- Оставлять доступные пользователю элементы без `agent-action-id`.
- Исполнять команду на промежуточном транскрипте.
- Переставлять кандидатов после заморозки (§5).
- Исполнять команду с незаполненным обязательным слотом (§8.3).
- Дублировать в этом документе параметры Θ (§8.3).
- Править `resolver.js` под форму данных хоста — адаптируется вход (§2).
- Называть видовую команду именем без префикса `show` (§7).

## 13. Решения по вопросам, открытым в rev 3

1. **Окно фолбэка.** Оптимистичного применения нет — §9. Причина: команда
   неизвестна до ответа сервера, применять нечего.
2. **Отсутствие сети.** Сырой транскрипт становится новым элементом,
   запись помечается как нераспознанная — §9. Причина: отпускание в
   мёртвой зоне самый частый жест, терять речь недопустимо, а копить
   очередь означает применять команды в непредсказуемый момент.
3. **Расхождение снимка с источником.** Вне зоны ответственности модуля.
   Модуль применяет патч к снимку, который ему дал хост; согласование с
   источником и разрешение конфликтов — обязанность хоста (§2).
4. **Регистр статусов.** Стандарт не фиксирует ни набор статусов, ни их
   регистр. Резолвер цели работает со своей парой `open`/`closed`, хост
   приводит свои статусы к ней в адаптере снимка (§2). Конкретное
   отображение для этого репозитория — в `PROPOSAL_voice-input.md`.
