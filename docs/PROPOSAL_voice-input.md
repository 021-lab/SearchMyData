# PROPOSAL: голосовое управление списком

Статус: предложение, 2026-07-23. Ветка `Voice-list-interface` от `codex-list-interface`.

Отдельное предложение: голос добавляется поверх существующего списка, не
переписывая его. Оценивать и принимать это предложение можно независимо от
остальной работы над списком.

---

## 1. Что есть сейчас

- Список и управление им — работающий модуль (`list-manager.html`, `src/`).
- `src/list-interpreter.js` — **исполнитель**: принимает готовую команду
  `{command, actId, payload}` и возвращает `{patch, actionLogEntry}`, а для
  видовых команд — `viewMode`/`effect`. Разбора текста в нём нет.
- Интерактивные элементы уже размечены `agent-action-id`.
- Голосового ввода нет вообще.

## 2. Что предлагается

Добавить **отдельный модуль голосового ввода**, который формирует команду и
передаёт её на исполнение существующему исполнителю. Исполнитель остаётся
единственной точкой изменения состояния и почти не трогается — см. §5.

Поток:

```
жест + речь  →  ПРИЁМ ВВОДА  →  РАСПОЗНАВАТЕЛЬ  →  ИСПОЛНИТЕЛЬ  →  патч
                   новое           новое          существующий
```

Ключевое разделение терминов, иначе неизбежна путаница:

| Слой | Что делает | Где |
|---|---|---|
| Распознаватель | `текст + контекст + снимок → кандидаты-команды` | новый |
| Исполнитель | `команда → патч + запись журнала` | `src/list-interpreter.js` |

## 3. Модель взаимодействия — коротко

- Долгое удержание в любой точке экрана открывает полноэкранный оверлей.
- Вверху — живая транскрипция. Вверх от пальца — кандидаты, ближайший
  наиболее вероятен. Точка пальца — «как есть». Ниже — отмена.
- Свайп влево по элементу открывает тот же оверлей, но с прицепленным
  контекстом — идентификатором этого элемента.
- Отпускание = выбор. Команда исполняется только после финального
  транскрипта.

Полное описание — `docs/INPUT_HANDLING_STANDARD.md` в этой же ветке.

## 4. Границы изменений

**Добавляется:**

| Файл | Статус |
|---|---|
| `docs/INPUT_HANDLING_STANDARD.md` | В ветке. Стандарт приёма ввода, rev 3 |
| `docs/TASK_RESOLVER.md` | В ветке. Алгоритм сопоставления цели, параметры Θ |
| `resolver.js`, `test_resolver.js` | **Отсутствуют** — см. §7 |
| модуль приёма ввода | К разработке. Жесты, пороги, оверлей |
| модуль распознавателя | К разработке. Словарь команд, ранжирование кандидатов |
| адаптер ASR | К разработке. Источник промежуточного и финального транскрипта |
| адаптер фолбэка | К разработке. Отправка сырого транскрипта, приём готовой команды |

**Изменяется:** исполнитель — только две новые команды (§5).

**Не изменяется:** рендер списка, хранилище, синхронизация, доменные
экраны.

## 5. Чего не хватает в исполнителе

Словарь голосовых команд не исполним без двух добавлений:

| Команда | Класс | Почему нужна |
|---|---|---|
| `setParent` | мутирующая | «перенеси в …», «сделай подзадачей в …». Есть `addChild` (создать ребёнка), но сменить родителя существующему элементу нечем |
| `search` | видовая | «найди …», «покажи …». Есть `showList`/`showFrontier`, но нет выборки по запросу |

Обе добавляются по существующему контракту. `search` — видовая: патч
пустой, запись журнала не создаётся.

## 6. Что отменяется

Прежний стандарт приёма ввода (rev 2) прямо запрещал то, на чём держится
эта модель: свайп игнорировался как жест, а сдвиг пальца более ~12 px
отменял начатую запись и закрывал оверлей. В rev 3 сдвиг — основной
механизм выбора, свайп влево — способ прицепить контекст.

Реализации по rev 2 несовместимы. Брать rev 2 как канон нельзя.

## 7. Незакрытая зависимость: код резолвера

`docs/TASK_RESOLVER.md` в ветке есть — §§1–4.4 описывают алгоритм, ярусы
совпадения, подписи `(m, s, t)`, правила R1–R3, инварианты и полный набор
параметров Θ. Этого достаточно, чтобы понять и проверить решение.

Чего нет:

- **`resolver.js`** — эталонная реализация. Экспортирует `queryPatterns`,
  `buildQuery`, `findCandidates`, `resolve`, `resolveOverTasks`. Прогнана,
  11/11 PASS.
- **`test_resolver.js`** — корпус на графе «Ремонт», CI-ready.
- **Тестовый корпус §5** документа — восстановлен только заголовок.

Оба файла существуют в локальной копии вне git. Первый шаг §8 — положить
их в репозиторий как есть. Переписывать алгоритм заново не нужно и вредно:
параметры Θ калибруются под корпус, новая реализация обесценит калибровку.

## 8. Этапы

1. Положить `resolver.js`, `test_resolver.js` и корпус §5 в репозиторий (§7).
2. Добавить `setParent` и `search` в исполнитель, с тестами (§5).
3. Слой приёма ввода: жесты, пороги, оверлей без распознавания —
   проверяется на заглушке кандидатов.
4. Распознаватель: словарь без контекста и с контекстом, ранжирование,
   заморозка порядка.
5. Фолбэк на модель и тост.

Этапы 1–2 не зависят от 3–5 и могут идти параллельно.

## 9. Приёмка

- Прокрутка списка не ломается ни одним из новых жестов.
- Строка под пальцем не подменяется после начала выбора.
- Команда не исполняется на промежуточном транскрипте.
- Команда с незаполненным обязательным слотом не исполняется частично.
- Видовые команды не создают записей журнала.
- Весь путь пользователя проходится автотестом через поле ввода, без
  синтеза речи.
- `node test_resolver.js` проходит в CI.

## 10. Открытые вопросы

1. Изменяется ли список оптимистично в окне между отпусканием и ответом
   фолбэка, или строка появляется только по ответу.
2. Поведение при отсутствии сети: отпускание без смещения — самый частый
   жест, а фолбэк требует сервера.
3. Расхождение локального снимка с источником данных в момент коммита.
4. Регистр статусов в словаре команд и в API данных требует сверки.
